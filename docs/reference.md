# timeskip reference

The details behind [README.md](../README.md): the project conventions, the scheduling and faults, the results, and how it works, including the protocol between the CLI and the guest.

## Your own project

`timeskip test` (or `timeskip test path/to/compose.yaml`) tests an ordinary Compose project, on what `docker compose up --build` would build plus your edits (with `--no-build`, on the images as they are, as Antithesis takes them), as `docker compose watch` applies them. It packs the project, its images included, into a bundle in the cache; `timeskip bundle -o app.tsb` writes one to run elsewhere with `timeskip test app.tsb`, on the same architecture: it holds what `test` tests here, the sync rules' files included, and the same project gives the same bytes.

- **The system** is the project's default-profile services, as `docker compose up` starts them. Every image goes into the bundle: the VM has no network. Images are pulled as Compose would, by `pull_policy` (`always`, `missing`, `never`); images in other profiles are bundled too, unstarted. Images are for the host's architecture, or a service's `platform:`; on macOS, linux/amd64 images (`platform: linux/amd64`, or pulled images with no arm64 variant), the only ones Antithesis runs, run emulated by QEMU, slower but unchanged. A service built from source has an `image:` name, and its `build:` uses only `context`, `dockerfile`, `args` and `target`. Bind mounts and `file:` configs and secrets of paths in the compose file's directory go into the bundle, as Antithesis's config image holds them; other host paths are refused, but the VM's own `/var/run/docker.sock`, `/proc`, `/sys` and `/dev` are fine. `internal: true` networks are refused: they'd cut the project off from Antithesis's network. The compose file is resolved as Antithesis resolves it, with its directory's `.env` and none of the shell's variables (timeskip notes when they'd make a difference).
- **Setup is complete** when a container appends `{"antithesis_setup": {"status": "complete", "details": null}}` to `$ANTITHESIS_OUTPUT_DIR/sdk.jsonl`, as for Antithesis; the Antithesis SDKs' `setup_complete` does it. Before that, a container that exits with a code other than 0, 137 (SIGKILL) or 143 (SIGTERM) fails setup.
- **The tests** are test templates: directories `/opt/antithesis/test/v1/<template>/` in a running container, holding executables named `<prefix>_<name>` with the prefixes `first_`, `parallel_driver_`, `serial_driver_`, `singleton_driver_`, `anytime_`, `finally_` and `eventually_` (see "Timelines"). Files starting with `helper_`, and subdirectories, are left alone; other files without a prefix, or not executable, are invalid commands and fail every timeline, as in Antithesis. A project without test templates runs by itself, its workload in its containers' entrypoints: a timeline is `timeout` seconds of it (see Settings), with faults if asked.
- **Results** are Antithesis SDK assertions. The SDKs write them through `/usr/lib/libvoidstar.so`, which timeskip mounts into every container as Antithesis injects its own, or to `$ANTITHESIS_SDK_LOCAL_OUTPUT`; a command can also append lines like `{"antithesis_assert": {"id": "every ping is answered", "message": "every ping is answered", "assert_type": "always", "display_type": "Always", "condition": true, "hit": true, "must_hit": true}}` to `$ANTITHESIS_OUTPUT_DIR/sdk.jsonl` (with `"hit": false`, a line declares an assertion that may never be reached). Each service has an `ANTITHESIS_OUTPUT_DIR` of its own; timeskip sets it, `ANTITHESIS_SDK_LOCAL_OUTPUT` and `ANTITHESIS_STOP_FAULTS` in every container.
- **Edits**: a component you rebuild on the host, test commands included, has a `develop.watch` rule, as for `docker compose watch`, e.g. `{action: sync, path: ./test, target: /opt/antithesis/test/v1/main}`.
- **Settings**: the project's compose file can hold an `x-timeskip` block, which Compose and Antithesis ignore and the bundle carries; `--set KEY=VALUE` overrides one of its keys for a run (and a failed property's replay line repeats it):

  ```yaml
  x-timeskip:
    faults: high_availability   # or resilient, legacy, none (see Faults)
    disk_faults: false          # or true, or a list of fail, full and power
    fault_gap: 10               # guest seconds between faults, about (see Mixing)
    drivers: 10                 # driver launches per timeline (see Timelines)
    timeout: 3600               # guest seconds a timeline may run
    memory: 4                   # the VMs' memory, GiB
  ```

`test` builds an image when its inputs changed since it was built: its build options, Dockerfile and context (less what `.dockerignore` excludes and sync rules deliver), and its `rebuild` rules' paths. After a rebuild the project is set up again before the timelines run; the images it doesn't build stay loaded in a checkpoint of their own. Bundling needs Docker, except that with its daemon stopped (to leave its VM's CPU and memory to timeskip's, say) a run uses the cached bundle as it is when nothing in it would change: each built image's inputs unchanged since it was built, and the bundle holding that build's image; the images the project doesn't build as they were pulled then. Otherwise the run fails, saying to start Docker. (A run that must set the project up again, after a kit update or a new `memory`, needs Docker too, to load the images it doesn't build.) So with a project whose binaries are built on the host and delivered by sync rules, Docker can be stopped once a run has bundled and set it up. Each timeline then applies the sync rules: each rule's path, less what Compose leaves out (the build context's `.dockerignore`, `.git`, editors' temporary files, the rule's `ignore`, and what its `include` doesn't match), is copied into the running service with the host files' owners where it differs, and what was deleted on the host since the image was built is deleted. (To tell, setup keeps a digest of each file under the rules' targets, and a timeline compares the host's files' digests to those, reading only container files changed since setup: disk reads take real time.) A changed `sync+restart` rule then restarts its service (and dependents that set `depends_on` `restart: true`). `restart` rules do nothing (they're for bind-mounted files), and `sync+exec` rules are refused.

**Tests that start containers** (dockertest, Testcontainers): give the test container the VM's Docker socket (`volumes: [/var/run/docker.sock:/var/run/docker.sock]`) and `network_mode: host`, so that the ports of the containers it starts are on its `localhost`. List each image they start, under the exact name they use, as a service in a profile that's never started; the VM can't pull one. (Antithesis allows the socket too, with the images uploaded.)

## Timelines

`timeskip test` runs `--timelines N` timelines of each template (default 1; `--template NAME` picks templates), up to `-j` at a time (default: one per CPU core, and never more for all the runs on the host together, as a VM that waits for a core waits in guest time (see How it works), and two VMs on one core's hardware threads each take up to twice the CPU time; on macOS, one per performance core). A timeline's seed (the first is `--seed`, or random; the next ones count up) chooses its schedule, as the Test Composer does:

- one of the template's `first_` commands, before anything else (its result is checkpointed and shared by the timelines that chose it);
- then either one `singleton_driver_`, the only driver, or `drivers` (default 10) launches of `parallel_driver_` commands (in the background) and `serial_driver_` ones (alone), with random pauses of up to 0.5 s between them;
- all along, `anytime_` commands at random moments (in a template with no drivers, `drivers` launches of them);
- and an ending, after drivers: a `finally_` command once every driver finished, or an `eventually_` command at a random moment, after killing whatever still runs.

The seed also seeds the guest kernel's random number generator once the `first_` command ran, and from then on nothing else feeds it (not interrupt timings, nor the host's randomness), so processes that ask for random numbers in the same order get the same ones. The same seed gives the same schedule, faults and random numbers; what the system does with them can still differ, since the guest's clock runs at the host's speed while it computes. A timeline that runs longer than `timeout` seconds of guest time (default 3600) is stopped, what still runs killed; that alone doesn't fail it, but as Antithesis's "All commands were run to completion at least once", each template needs a timeline that completed. `--no-skip` runs in real time.

`--max-failures N` stops the run early once N timelines have failed: no more timelines start, those running are stopped, and the report covers the timelines that ran, listing the others as `not run` (`results.json`'s `not_run`; they have no result, and count toward no property). `--max-failures first:N` counts only the timelines that failed in their `first_` command (it exited other than 0) or before it (the edits couldn't be applied), as such a failure usually repeats in every timeline, while a later failure is worth seeing across all the seeds.

**Faults.** timeskip injects faults as Antithesis does, from the end of the `first_` command until the ending, which starts once every fault is healed (permanent clock skips stay). `faults` (see Settings) picks one of Antithesis's fault tolerance levels: `high_availability` (the default), `resilient`, `legacy`, or `none` for no faults. Faults apply to the project's containers, test commands' included, not to containers that share the VM's network or that a test starts itself:

- a baseline latency on everything the containers send: a realistic, varying delay (a paretonormal distribution around 0.1 to 1 ms) and a low loss rate;
- thread pausing, at every level as in Antithesis: now and then the guest kernel holds a thread in a container off the CPU for 10 µs to 10 ms of guest time (as likely in each octave), at a scheduler tick while it runs (one in 8; a tick is 4 ms) or as it's switched in (one in 16), so that threads interleave differently in each timeline. Every container's threads are paused (those a test starts included), never timeskip's own. As in Antithesis, the pauses aren't listed (the console log counts them);
- network faults, one at a time: partitions (two sides, or one way only) and clogs (some containers' inbound, outbound or both), whose packets are dropped (stopped), delayed by 20 ms to 1 s (slowed) or held until the fault heals (jammed: up to 64 MiB per container and network, then dropped); `resilient` makes only slowed or jammed clogs;
- with `resilient` (pauses and throttles only) and `high_availability`, node faults, one at a time and independently of the network faults: a pause, a stop (SIGTERM, then SIGKILL after 10 s), a kill or a throttle (each of its containers limited to 5% to 50% of a CPU, by its cgroup's `cpu.max`) of one container three times in four, else of two or more, healed by unpausing or starting again what it took down, or lifting the limit. A container that shares another's network is part of its node. Test commands in a paused container pause with it, and those in a stopped or killed one are killed, which doesn't fail them; then the timeline runs no `finally_` command, since not every driver completed.
- with `resilient` and `high_availability`, CPU modulation, independently of the others: the CPU speed of every container together, those a test starts or that share the VM's network included (the bandwidth of Docker's cgroup), changes every 0.1 to 1 s, between 10% and 100%. As in Antithesis, no exclusion spares a container from it.
- with `resilient` and `high_availability`, clock skips, on a schedule of their own: the wall clock (`CLOCK_REALTIME`) jumps forward or back by 10 ms to 30 s, half the time for 0.1 to 30 s and then back, else for good (its `ms` is 0); skips stack. The monotonic clocks (`CLOCK_MONOTONIC`, `CLOCK_BOOTTIME`, what timeouts and `sleep` use) and the CPU's cycle counter don't jump. The VM has one wall clock, so a skip is every container's, as Antithesis's shared clock is every node's; so excluding any container from clock skips turns them off.

- with `disk_faults`, which no level makes (Antithesis injects no disk faults), disk faults of the kinds it lists (`fail`, `full` and `power`; `true`: all that the level allows) on nodes' disks (see below), independently of the others, one at a time, of one node three times in four, else of two or more (with zones or regions, a zone's or region's one time in four, as node faults), until the fault heals:
  - a failing disk (`fail`) fails 1% to 100% of its reads and writes of file data with `EIO`. A write that failed is lost, and the next `fsync` reports it (Linux marks the page clean: its data is gone once it leaves the cache); a read that failed returns `EIO` (`SIGBUS` through an `mmap`). Writing it again and `fsync`ing makes it durable (the guest's kernel fixes Linux 6.12's ext4, which then loses a rewrite of a block it had just allocated or preallocated, though `fsync` succeeds). Creating, removing or renaming a file and `fsync`ing a directory (metadata) fail with `EIO` as often, before they change anything; the filesystem's own reads and writes (its metadata blocks, its journal) never fail, so it stays whole (see Differences). As the fault heals, the containers that exited with an error code meanwhile (as systems that stop on a failed write do; not on `SIGILL` or `SIGSEGV`) are started again, and their exits aren't unexpected ones; any other exit is a crash, as ever. Half the failing disks (`a reboot as it heals` in their `detail`) reboot each node whose reads or writes failed as they heal, as a machine is rebooted after a disk failure, for systems that recover from an I/O error only by restarting (NATS's Raft holds on to one): its running containers are killed, its disk is mounted again (the kernel's caches of it are gone) and they're started again. The others leave them running, for systems that should recover by themselves. A read that failed leaves a 4 KiB block of it bad, as a latent sector error does: reads of it fail until it's written again or the fault heals. Nodes excluded from kills get no failing disks.
  - a full disk (`full`) has no space left (`ENOSPC`): a file of the fault's takes it, and the heal removes it. Containers that exited with an error code meanwhile are started again, as after a failing disk.
  - `power` (with `high_availability`) makes half the kills power losses (`"detail": "power loss"`) instead of its own faults: the node's disk loses its power too. Its containers are frozen, its filesystem is shut down at once (it writes nothing more, its journal included) and they're killed; then the disk loses some of what its volatile cache held, each 4 KiB block written since its last flush with probability one half (so a write that wasn't flushed may be lost, torn or reordered), and it's mounted again, replaying its journal. So what was `fsync`ed survives and what wasn't may not, data or metadata, as after a real power cut: a file created, renamed or removed since the journal's last commit (ext4 commits every 5 s, and at each `fsync`) is as it was before, and a file's unsynced end may be missing or read as zeros. A node excluded from kills (`kill` in the label) or from disk faults has no power losses.

A harness should assert durability only of what the system `fsync`ed before acknowledging it, or run the system in its durable mode (NATS: `sync_interval: always`), and keep its own records off nodes with disk faults (`disk` in `com.antithesis.exclude_from_faults`) unless it `fsync`s them.

A throttled container waits for its cgroup's next period (100 ms) once it used its quota, and the clock skips to it if nothing else runs: its work takes guest time as on a slower CPU, but no wall time.

**Exclusions.** A container labeled `com.antithesis.exclude_from_faults` with a list of `network`, `pause`, `stop`, `kill`, `throttle`, `clock` and `disk`, as some Antithesis projects are, excludes its node from those: with `network`, it's never a partition's or clog's target (its traffic with the targets is disrupted with them); with `clock`, there are no clock skips at all. Label a harness container that must not go down with all seven, as Antithesis's `antithesis.fault_exclusions` would exclude it. As in Antithesis, no label spares a container from thread pausing.

**Zones and regions.** A container labeled `com.timeskip.zone: NAME` puts its node in zone NAME, as an availability zone, and `com.timeskip.region: NAME` in region NAME. Zone names are global, as AWS's are (`us-east-1a`): one zone is in one region. When the nodes are in two zones or more, or two regions, half the network faults take a zone or region (each half the time, if both): a partition sets its nodes apart from the others (or only one way), a clog takes its nodes' traffic with every node outside it; and one node fault in four takes every node of a zone or region at once (with `high_availability`, an outage). What a node sends to a node in another zone of its region gets a higher baseline latency, 0.25 to 1 ms more each way, and to another region 5 to 50 ms more. Exclusions apply as to other faults: an excluded node is left out of its zone's and region's faults. A node with no zone or region is in none, and its traffic gets the plain baseline. These faults say `zone NAME` or `region NAME` in their detail. Antithesis ignores the labels: there, the same project runs without them.

The seed chooses each fault, its targets, when it starts (up to the timeline's gap after the last one ends: see Mixing) and how long it lasts (0.1 to 30 s of guest time). Faults show in the console log and in `results.json`, from when they start to when they're healed; a stop starts with its SIGTERM, and its line, printed once the container stopped, says when that was (`since 1.10s`). As in Antithesis, a test command can run `"$ANTITHESIS_STOP_FAULTS" SECONDS`: the faults in effect are healed before it returns (a stop under way first runs its course, up to 10 s), and no new ones start meanwhile, nor for SECONDS after; but the baseline latency stays, and clock skips go on, as Antithesis's do. With `faults: none` it does nothing.

**Mixing.** Timelines differ in their kinds of fault and in how many they get. Each draws its gap, the most guest time between one fault's end and the next one's start, from a third of `fault_gap` S (default 10 s) to three times it, log-uniformly; each fault then starts S/100 to S of that gap after the last. With `resilient` or `high_availability`, a coin from the seed also leaves the node faults (pauses, stops, kills and throttles) out of half the timelines, and makes their other faults three times as dense (a third of the gap). Node faults find some bugs and hide others: a kill or a stop restarts what a bug needs to stay up in a bad state, and a pause stops a lagging node from showing it. With the coin, `high_availability` finds most bugs for far less CPU time than `legacy`, without losing on the bugs node faults hide, at up to twice the cost on bugs that only node faults find, as half the timelines go without them. `results.json` says each timeline's half (`fault_mix`) and gap (`fault_gap_ms`), and the console line says `(no node faults)`.

## Results

A run passes when, over all its timelines, every Always assertion held (and was reached, if `must_hit`), every Sometimes assertion was true at least once, every Reachable one was reached and no Unreachable one was (judged by `assert_type` and `must_hit`, as Antithesis does), every test command exited 0 (or was killed by an `eventually_` ending), and, as Antithesis's default properties have it, no test command was invalid, no container exited with a code other than 0, 137 or 143 (a stop fault's SIGTERM may make a process that catches it exit with any code: that exit doesn't count, as Antithesis doesn't count the exits of containers it stops, but a crash before the signal does), no process died of a program error signal (SIGSEGV, SIGBUS, SIGABRT and the like), and the VM didn't run out of memory (the kernel killing a process for it; Antithesis fails its "Peak memory usage" property already at 95%).

timeskip prints a line per timeline, the test commands and containers that used the most CPU (as idle time is skipped, CPU time is what a run takes), and a line per property, with a seed to replay each failed property; keeps the logs of failed timelines (ending with the services' last 50 log lines when a container failed) and of a failed setup, and for each of those (with one timeline too, whose console streamed) a `.containers.log`: every container's stdout and stderr from setup on, in order, each line timed in guest seconds since the timeline started (the timeline's last start, after a `first_` command; negative before it), which clock skips don't move; and exits 0 if the run passed, 1 if not, 125 if setup failed, 130 if interrupted, or 2 for usage and harness errors. `--out DIR` writes `DIR/results.json`, `{"pass", "timelines", "properties", "coverage"}`: each timeline's `template`, `seed`, `first` (its `first_` command), `from` (`setup` or `first`, the checkpoint it started from), `pass`, `not_run` (see `--max-failures`), `errors`, `commands` (`name`, `exit`, `killed`, `ms`, `cpu_ms`: the CPU time it and what it waited for used), `assertions` (`id`, `message`, `type`, `display`, `must_hit`, `hits`, `true`, `details`), `faults` (`kind`: `latency`, `partition`, `clog`, `pause`, `stop`, `kill`, `throttle`, `modulation`, `skip` or `disk`; `detail`, `targets`, `at_ms`, `ms`), `fault_mix` (`node faults` or `no node faults`, with a level that makes node faults) and `fault_gap_ms` (see Mixing), `guest_ms`, `skips`, `wall_s`, `container_cpu_ms` (the CPU time each container's cgroup used, test commands' included, by name) and, if it failed, `log` and `container_logs`; and each property's `name`, `type`, `pass`, `hits`, `true`, `failing_seeds` and `details`. `hits` and `true` count the lines the SDKs wrote, which is each process's first true and first false evaluation, not every evaluation. With one timeline the console streams to stdout, each command's output prefixed with its name.

With several timelines, each timeline's line is also printed as it ends, followed by how many have ended and failed so far (`; 12 of 48 done, 1 failed`), so that a long run shows its progress.

**Wake-ups.** Idle time is skipped only while every thread sleeps, so what a timeline takes is the CPU time its processes use and their wake-ups, each of which ends a skip. Each timeline's `wakers` in `results.json` are, of the processes running as it ends, the five of the containers and the three of the VM's own (the guest agent `timeskip-guest`, `dockerd` and `containerd`, which work for each test command and fault, and kernel threads, in brackets) that woke up most since setup (the `first_` command included): `container` (none for the VM's own), `process`, `pid`, `wakeups` (its threads' voluntary context switches: sleeps, each ended by a wake-up), `cpu_ms` (its CPU time, in steps of 10 ms: on the VM's one vCPU, time nothing else ran and the clock couldn't skip) and `every_ms` (guest time per wake-up, on average: a process that polls every 100 ms shows about 100). timeskip prints the five of the containers' that woke up most over the run, too (`most wake-ups`). The guest reads the kernel's own counts at the end of setup (kept in the setup checkpoint) and as the timeline ends, and does nothing in between; under `TS_DET` the counts are the same in every run of a seed. Processes that exited before the end, such as test commands, aren't counted, nor the wake-ups of a process's threads that exited (its CPU time includes theirs); and timer intervals only on average: telling them apart would take tracing the timers, which takes guest time.

**Profiling.** `--profile` (with `--out DIR`) samples the stacks of the containers' threads every 10 ms of the CPU time they use, as `perf record` would on Docker's cgroup (with a perf event the guest kernel schedules only while a container's thread runs, so idle time is still skipped), and writes each timeline's to `DIR/TEMPLATE-SEED.folded`: a stack a line, `container;command;outermost;...;innermost` and its samples, as `flamegraph.pl`, `inferno` and speedscope read them; it also prints the functions most samples were in. Kernel functions end in `_[k]`. User stacks are unwound by frame pointers, so code built without them (most C, and stripped binaries, which show `file+0xOFFSET`) shows little more than its innermost function, while Go's show whole. A process that exited before its samples were read shows as `[exited]`. Profiling costs about 10% more CPU time.

**Coverage.** Code instrumented for Antithesis (its Go instrumentor, or compilers' sanitizer coverage through the SDK) reports each edge of its control flow it reaches to `/usr/lib/libvoidstar.so`, as on Antithesis; timeskip's sets the edge's bit in a file per module that every container shares, and the files are in the checkpoints, so each timeline starts with what setup reached. For each instrumented module (named by its symbol table, as the instrumentor named it), timeskip prints how many of its edges the run reached, how many no earlier run with the same cache had, and how many were reached by each quarter of the timelines, with a verdict: still growing (more timelines may reach more) or levelling off (vary what the timelines do instead), as Antithesis's utilization graph of new behaviors over time. `results.json`'s `coverage` has each module's `module`, `edges`, `reached`, `new` and `progress` (edges reached after each timeline). With `--out DIR`, timeskip reads the modules' symbol tables from `/symbols` in the containers, as Antithesis does, and writes `DIR/MODULE.functions.tsv`: each function's file, name, line, edges and edges reached, and prints how many were never reached. Go programs report coverage when built with cgo, which loads libvoidstar; on macOS, emulated amd64 images get no libvoidstar, and so no coverage.

**Exploring.** With `--explore`, timeskip searches as Antithesis does, branching timelines from moments that did something new, rather than running only independent ones. When a timeline's instrumented code reaches edges no timeline of the run had, libvoidstar tells the guest agent, which tells the CLI, and the CLI saves the VM there; likewise when an SDK assertion reaches a state no timeline of the run had (its first hit, or a Sometimes assertion's first true, in any container's `sdk.jsonl`). The CLI saves the VM there, memory and disk, as a branch point (at most one a second of guest time per timeline), until the timeline fails (a command fails, an Always assertion is false or an Unreachable one reached, or a container exits unexpectedly: a branch would inherit the failure) or its ending comes (its `finally_` or `eventually_` command, or with none, the end of its drivers: a branch could do nothing new). And when a timeline fails, the branch points it saved in the last second of guest time before are withdrawn: by then the failure was mostly settled, if not yet checked, and timelines from there would find it again. Half the timelines start from setup; the others, alternating with them, from the branch point worth the most: worth its new edges, and for each new assertion state as much as the most a branch point was so far, since its author called it out; divided by one more than the timelines that branched from it so far. A timeline never waits for a branch point: with none to start from (none yet, or all still being saved), it starts from setup, and later ones branch to make up the share. A timeline from a branch point goes on from that moment, its commands still running, with its own seed from then on: the schedule's remaining choices, the faults', the kernel's random numbers and thread pauses. What was drawn before the moment stays: the waits then running (for the next launch, `anytime_` command, fault or clock skip) and the moment of the `eventually_` ending, which sets how long the timeline runs, are drawn anew too, the ending's over what's left of its window. Its results include what happened before the moment (its commands, assertions, coverage and log), and say where it branched from (`from branch: seed 12 at 3.4 s`, and `results.json`'s `branch`: `seed`, `at_ms`, and `from` for a branch of a branch). Exploring, each assertion's `first_false_ms` is when it was first false (an Always assertion) or reached (an Unreachable one), and each timeline's `failed_ms` when it first failed, as the guest saw it, so that a failure after the branch point can be told from one before it. Each template keeps up to 32 branch points, a new one taking the place of the one worth the least if it's worth more; and since a save costs a copy of the VM's memory and disk, a timeline saves one only if the timelines left to start from branch points couldn't all start from ones worth as much (counting that each pick lowers a point's worth). On Linux, branch points are saved in memory, in `/dev/shm/timeskip-UID`, while it has room and the host has a quarter of its memory available, and otherwise in the cache: on a disk, the half a gigabyte or so each takes would be written out within half a minute (Linux's default `vm.dirty_expire_centisecs`) or at its limit of dirty pages, and saves would wait for the disk. The run prints the branch points saved and the time that took (`results.json`'s `saves` and `save_s`, per timeline), and how many timelines started from how many of them. Exploring pays when `--timelines` is several times `-j`: timelines that start together can't branch from each other. The branch points a failed timeline started from are kept in the cache (`results.json`'s `branch.checkpoint`), and `--branch DIR --seed N` replays from one. Branching pays when a timeline must first get through a long, costly stretch to a rare state from which the bug is near, and an assertion marks that state (a Sometimes assertion that's seldom true): branches then start there instead of from setup. Without such a marker, as many independent timelines (no `--explore`) find bugs for as little CPU time.

## How it works

A service's image by digest (`redis@sha256:HEX`) is loaded from the bundle as `redis:sha256-HEX`, since `docker load` doesn't keep digests, and the guest's compose file names it so. Containers network as on a Docker host, less what the VM doesn't need: dockerd sets up no iptables rules (but its embedded DNS server's, in each container), so containers on a network reach each other by name, published ports are on the VM's addresses, and nothing routes between networks. Containers get a Docker host's limits (open files 1048576, no process limit) and `vm.max_map_count` 262144; Docker's disk is 64 GiB, allocated as it's used. Each node (a container with a network of its own, and the containers on its network) has a disk of its own too, as a machine does: an ext4 filesystem of 64 GiB, allocated as it's used (a loop device over a file on Docker's disk, with direct I/O, so that it's cached once), that holds its containers' own layers, the volumes no other node mounts and the project's files bind-mounted into its containers alone. Volumes and files that nodes share, and the containers tests start, stay on Docker's disk. The VM has one vCPU and 4 GiB of memory (`memory`; Antithesis's machine has 10, which costs timeskip some speed and disk). The Compose project is named `antithesis`, so containers are `antithesis-<service>-1`.

The guest's userland (Alpine, Docker and Compose, and the guest agent) is a read-only EROFS image in the kit, each VM's root disk. Once per kit, the CLI boots a VM with a blank data disk and saves it, memory and disk, once dockerd is up: the base checkpoint. A bundle's first `test` restores it (or an images checkpoint, of the images the project doesn't build, set up from the base) and gives it the bundle: the guest agent loads the images, creates the project's containers (`docker compose create`), gives each node its disk, starts them (`docker compose up -d`), waits for `setup_complete` and then for a moment when every thread sleeps, and reports READY with the test templates it found. The CLI saves that VM as the bundle's setup checkpoint. Every timeline is a new VM restored from a checkpoint, with a copy-on-write clone of the disk and the saved memory mapped copy-on-write: a restore takes milliseconds. The first timeline to run a template's `first_` command saves the VM again afterwards, so that later timelines with the same `first_` (and the same edits to `first_` and `helper_` files) start after it. Checkpoints are named by the bundle's contents, the kit (and on macOS the OS build, on Linux the kit's path) and kept on disk in the cache (`TS_CACHE`, default `~/.cache/timeskip`; on APFS, XFS or btrfs disks are instant clones), one kit's at a time, and a bundle's latest version's: a new version replaces its checkpoints, as a new version of a template's `first_` and `helper_` files replaces the checkpoint after its `first_` command. Of the failed timelines' logs that runs keep, the cache keeps the last 10 runs', and of their branch points the last 3 runs' (a run's take gigabytes); and it removes what no run used for 5 days (checkpoints, cached bundles, logs and branch points), cached bundles whose project is gone, checkpoints whose bundle is gone, and branch points whose setup checkpoint is gone. A run removes what else it made as it exits, whether it ends or is stopped (Ctrl-C, SIGTERM, SIGHUP), and the next run removes what a run that was killed (SIGKILL) left.

A VM's clock runs with the host's while the VM runs, and skips while it idles. What its vCPU didn't run of that time, as the host ran other threads or (under hvrun) handled the VM's disk I/O, the guest counts as stolen time (`/proc/stat`'s steal: KVM's steal clock under Firecracker, SMCCC's paravirtualized time under hvrun), not as CPU time of the task it took from. So a loaded host makes work take more guest time, but not more CPU time.

The CLI and the guest agent (`cmd/guest`) talk over the VM's console (`hvc0` under hvrun, `ttyS0` under Firecracker) in lines of the form `TS <nonce> VERB ...`. The nonce is 12 random hex digits per checkpoint, passed on the kernel command line; the CLI ignores lines that don't start with it, so command output isn't mistaken for control lines by accident.

| Direction | Line | Meaning |
| --- | --- | --- |
| guest → host | `BASE {}` | (Booting a VM for the base checkpoint.) dockerd is up and the VM idle; the CLI saves it. |
| host → guest | `SETUP bundle=virtiofs` or `SETUP bundle=blk:SIZE` | (Restored from the base or an images checkpoint.) Set up the bundle: `bundle.tsb` on the virtiofs share (macOS), or the first drive, swapped in (Firecracker). |
| guest → host | `READY {"catalog": ...}` | Setup is complete and the VM is idle, with skipping off, disks synced and memory freed during setup zeroed. The CLI saves it. The catalog lists each template's commands. |
| host → guest | `GO skip= seed= template= first= firsts= drivers= timeout= pre= checkpoint= inputs= faults= level= disk= profile= symbols= explore=` | Run a timeline (the fields are `protocol.Go` in `internal/protocol`); `faults=` is `fault_gap` in seconds (0: none). Edits arrive on a virtiofs share (macOS) or as an image swapped into the third drive (Firecracker). |
| guest → host | `CHECKPOINT {}` | (With `checkpoint=1`.) The `first_` command ran and the VM is idle; the CLI saves it, then sends `CONTINUE`. A VM restored from that checkpoint gets a `GO` there instead, and goes on with its seed and inputs. |
| host → guest | `CONTINUE` | Go on, after `CHECKPOINT`. |
| guest → host | `EDGES {"at_ms": ..., "edges": ...}` | (With `explore=1`, as the drivers run.) What the timeline did for the first time in the VM (`edges`: instrumented code's edges, by module; `assertions`: `reached KEY` and `true KEY`, by the assertion's ID or else message); the CLI may save the VM there, as a branch point, then sends `NOTED`. The guest sends no `EXIT` meanwhile, and skips no idle time, which would go by at once while the CLI saves the VM. |
| host → guest | `NOTED` | Go on, after `EDGES`. |
| host → guest | `BRANCH seed=` | (To a VM restored from a branch point, instead of `NOTED`.) Go on with this seed's random numbers, and draw anew the waits drawn before. |
| guest → host | `EXIT {"kind": ...}` | The end: `timeline` with its commands, assertions, errors and faults; `setup` with what failed, its containers' logs written as for `LOGS`; or `replan` with a new catalog, when edits changed the template's `first_` commands. |
| host → guest | `LOGS` | (After a failed timeline's `EXIT`.) Write the containers' logs to the data disk's last GiB, past Docker's filesystem, for the CLI to read from its copy of the disk; once, at the end, so that the I/O neither keeps idle time from skipping nor changes the timeline. |
| guest → host | `LOGGED {}` | They're written. |

## Differences from Antithesis

A project that runs in timeskip runs unchanged in Antithesis, and timeskip fails what Antithesis's default properties would, with these exceptions:

- Antithesis explores by default, and from any moment its search finds interesting; timeskip only with `--explore`, and from moments that reached new edges of instrumented code or new assertion states, so a project with neither gets independent timelines.
- The VMs have 4 GiB of memory unless `memory` says otherwise; Antithesis's has 10 GB.
- On macOS the VMs are arm64, so images with an arm64 variant run it, and amd64 ones run emulated, without libvoidstar (their SDKs write to `ANTITHESIS_SDK_LOCAL_OUTPUT`). Antithesis runs amd64 only.
- Faults: thread pausing needs no instrumentation (the guest kernel pauses threads at ticks and context switches, rather than at instrumented code); one network fault at a time; a jam delivers what it held when it heals; a restarted container keeps its filesystem, and Docker leaves a `restart:` policy out of it; the quiet time of `ANTITHESIS_STOP_FAULTS` counts from when the faults are healed.
- Clock skips can be turned off: Antithesis lets no exclusion spare a node from them.
- Zones and regions (`com.timeskip.zone`, `com.timeskip.region`) are timeskip's own: Antithesis has none.
- Mixing is timeskip's own: Antithesis gives every timeline its level's faults.
- Disk faults (`disk_faults`, and `disk` in `com.antithesis.exclude_from_faults`) and nodes' disks are timeskip's own: Antithesis injects no disk faults. A failing disk's errors are random, but for the blocks failed reads leave bad, and a metadata operation fails before it changes anything, never leaving the filesystem read-only as a real disk's errors may; a power cut loses whole 4 KiB blocks of the cache, never part of one; and volumes that nodes share are on a disk that never fails.
- CPU modulation varies the containers' CPU bandwidth, not the processor's clock or the relative speed of its instructions, and doesn't slow Docker. Antithesis's docs put node throttles in no fault tolerance level; timeskip makes them where it makes pauses.
- The `first_` command runs with the same random numbers in every timeline, since what it leaves is checkpointed and shared, and setup ends at a moment when every thread sleeps, after `setup_complete`.
- Antithesis has no `timeout`: a command that hangs there runs out the timeline.
- Assertion catalogs that Antithesis makes when it instruments Java, Python and .NET (`/opt/antithesis/catalog`) aren't read, so an assertion those languages never reach isn't reported. (Go, Rust, C++ and JavaScript catalog their assertions as they start.) Nor is memory usage checked, short of running out.
- SDK versions that truncate their output file when a process starts (before their releases of August 2026), when they write to `ANTITHESIS_SDK_LOCAL_OUTPUT` rather than through libvoidstar (Go built without cgo, Java), lose their service's earlier output.
- Containers resolve each other through Docker's DNS on their networks, not `/etc/hosts`, and Docker's disk is ext4, not tmpfs.

## Compatibility

From version 1.0, within a major version: the CLI's flags, `x-timeskip` settings, exit codes and `results.json` fields keep their meaning (fields may be added). Bundles carry a format version, and timeskip refuses a bundle of another one: write it again with the same timeskip's `bundle`. Checkpoints and the rest of the cache belong to one kit, and a new kit makes its own. The CLI and the guest ship together, so the protocol between them can change with any version.
